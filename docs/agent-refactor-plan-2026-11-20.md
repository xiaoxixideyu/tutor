**tutor 教学策略与业务核心重构计划（评审稿，2026-11-20）**

建议采用有边界的重构：保留 Node 单进程、本机单用户、CLI 和网页，以及已有模型传输、会话日志、规则判分、搜索、内容验证和文件存储能力；重构教学决策、学习证据、状态提交和交互协议。

以下保留 2026-11-20 评审时的方案与阶段划分。用户随后授权全量实施，并取消兼容和迁移要求；最终设计与验收以 [当前架构](design.md) 和 [重构验收记录](agent-refactor-acceptance-2026-11-23.md) 为准。实际业务动作预算已依据修复场景调整为默认六步，并提供批量原子学习判断。

目前的结构是“程序选择工序，模型完成工序内的任务”。目标结构是“教学 agent 根据用户目标和学习证据选择行动，程序验证并可靠执行行动”。agent 的自主性体现在教学策略，而执行框架继续保持明确的工具边界、预算和事务规则。

### 1. 要达到的业务结果

学员只需表达目标、作答和反馈。系统应能判断当前缺少什么证据，选择解释、例子、诊断题、独立任务、复习或阶段验收，并根据结果修订后续安排。

课程可以先形成可执行的近期安排，再逐步补充后续结构。学员有充分基础证据时可以直接做任务；出现能力缺口时可以针对具体前置补测或补讲。教学行动的顺序由 agent 根据情况决定。

必须同时满足以下要求：

- 学习进度、能力判断、记忆状态、阶段验收分别表达。一次练习成绩只作为一条证据。
- 目标包含可观察的完成标准、范围和排除项。期限与可用学习时间参与计划可行性判断。
- 用户明确要求优先于 agent 的建议。扩大目标范围、改变承诺或重置既有进度，需要作为具体变更呈现给用户。
- 所有掌握判断和画像推断能追溯到证据；未知信息保持未知。
- 内容拒绝有实际修复路径，服务失败有恢复路径，暂停有明确断点。
- 页面刷新、查看进度和重放既有结果不调用模型。

### 2. 决策权与执行权

| 事项 | 教学 agent 的职责 | 程序的职责 |
|---|---|---|
| 下一步学什么 | 结合目标、证据、时间、正在进行的活动选择行动 | 提供状态和候选能力，校验目标范围与执行条件 |
| 课程结构 | 设计目标、技能关系、近期安排和调整建议 | 校验引用、版本、依赖类型及资源限制，保存修订 |
| 用户画像 | 提出能力缺口、误解、偏好等假设，选择验证方式 | 保存原始反馈及证据，标记自述、实测和推断的区别 |
| 教学方式 | 选择解释、例子、提示、独立任务和检验方式 | 渲染已验证内容，记录提示、题目曝光和作答 |
| 掌握判断 | 根据目标量规和证据提出判断与下一步 | 检查证据资格、量规版本和关键任务要求，提交评定 |
| 复习与补救 | 决定复习、补测、补讲的取舍和顺序 | 计算时间、记忆调度参考值，记录新的回忆证据 |
| 内容与成绩 | 生成候选内容、诊断和修复建议；独立会话执行语义评审 | 规则判分、格式校验、版本化审查、事务、回执和预算 |

程序保留的规则应主要是可确定验证的事实和边界。固定“复习优先于所有新课”“低分重上整节课”“一个知识点必定一节课”等教学策略，改为 agent 可调整的默认建议。

agent 提出的能力判断也需要约束：不能以自述、已展示答案、一次基础题或缺乏依据的信心值直接宣布目标达成。具体证据要求来自经验证的目标量规，而不是全课程共用一个分数阈值。

### 4. 领域模型与状态设计

| 对象 | 必须表达的内容 |
|---|---|
| Learner | 通用偏好、可用时间、自述背景；课程相关基础另行关联 |
| LearningGoal | 可观察的验收目标、范围、排除项、期限、优先级与用户原话 |
| Skill / Objective | 技能与具体检验目标、量规、前置和关联关系、内容版本 |
| Activity | 一次可恢复的教学活动；可覆盖多个目标，同一技能可对应多次活动 |
| Attempt / Evidence | 完整题面与版本、原始作答、评分依据、提示和曝光、时间、执行结果 |
| LearnerHypothesis | 推断的能力缺口或误解、依据的证据、待验证问题；不伪造精确概率 |
| CompetencyJudgment | 目标评定、依据、量规版本、关键要求是否满足、尚缺的证据 |
| MemoryState | 最近回忆、稳定性、失败记录与调度参考 |
| TutorDecision | 基于哪个状态版本、简短决策依据、选择的行动、预期证据、再判断时机 |
| CourseRevision | 当前目标、内容引用、活动与评定的版本，作为提交和缓存失效依据 |

课程单元保留为组织和展示方式。“技能”“一节课”“一次练习”不再互相等同。前置关系与一般关联分开表达，跨单元的有效前置不会被裁掉。

阶段验收按照目标要求判断。关键的独立任务失败时，其他客观题得分不能替代该目标。出现一次遗忘或失败时，保留既有成功证据和已完成的学习活动，增加冲突证据，由 agent 决定最小必要的补救。

默认继续采用文件存储。V2 将相互依赖的学习状态组织为单一版本化快照；大体积内容、原始证据和审查详情作为独立资产引用。提交先保存不可变资产，再原子切换当前状态快照；页面只能看到已提交状态。

每次修改使用 expectedRevision 和 requestId：短课程锁内校验版本、提交状态和回执。模型等待、用户思考和长任务不占用写锁。相同尝试重复提交返回同一回执；不同答案或过期题目版本需要新的合法尝试。

V1 YAML 保留为迁移来源和可读导出。每门课只有一种权威状态来源，避免长期双写。证据索引和看板摘要是可重建视图，不成为第二套事实来源。

### 5. agent 的行动范围与运行约束

首版提供少量业务能力工具：

| 能力 | 用途与边界 |
|---|---|
| inspect_learning_state | 获取目标、活动、证据和约束的精简快照 |
| ask_learner | 澄清缺失信息或发起已定义的诊断问题，随后交回用户 |
| create_activity | 按目标创建解释、例题、回忆、诊断、独立或迁移任务 |
| evaluate_attempt | 规则或独立判分服务；返回证据和评定候选，禁止直接改分 |
| propose_course_patch | 提出目标内的技能、近期安排和依赖调整，带版本和依据 |
| propose_learner_update | 提出画像假设或能力评定，引用已有证据并说明尚缺的验证 |
| plan_review | 结合记忆参考、目标与时间提出复习安排 |
| research_topic / repair_content | 持久化任务，返回证据、审查状态或具体失败原因 |
| finish_session | 结束、暂停、时间用尽、等待信息或阶段达成，使用明确结果类型 |

工具名和允许的动作由程序定义，教学动作的选择与组合由 agent 决定。显式“复习”“考试”“刷题”等命令作为用户指定意图执行；规则判分和已有零模型执行能力继续保留。默认“开始/继续学习”走教学 agent 的决策。

决策合并到当前教学回合或活动边界，避免为每个简单答案分别调用“规划模型”和“讲授模型”。页面只读取已保存的决策；新证据、目标变化、活动结束或决策过期才触发重新判断。

运行约束包括：

- 初版每个决策回合最多四个业务工具步骤，之后必须交回用户、等待任务或明确结束。限制可配置，并由真实记录调优。
- 成本预算覆盖全部能力、独立审查和传输重试，不能因新建会话而重置。
- 持久化决策、活动、任务与尝试；恢复沿用已有身份与已完成结果。
- 无法取得必要证据时，提出补测、补证或暂时限定结论，不凭空宣布掌握。
- 悬空引用、过期版本、越权范围、伪造证据与错误内容均返回结构化拒绝原因，供 agent 调整行动。
- agent 不获得任意文件写入和 shell 权限。自主执行实践代码只通过有文件、网络和资源隔离的执行接口。

记录的决策理由应简短并引用事实，例如：“你能判断切片共享，但独立复制任务仍修改了原切片，先检验复制后的存储关系”。不要求模型输出内部思维链。

### 6. 分阶段实施与验收

各阶段按可独立验证、可回滚的变更推进。首先完成一个课程的真实 agent 闭环，再扩大迁移范围。

**阶段 0：明确业务契约，建立回归基线。**

工作：冻结当前工作区与课程数据的可恢复基线；把本轮已复现的问题转成业务反例；明确目标达成、掌握判断、暂停、修复、预算和用户指定意图的规则。

交付：领域对象草案、规则归属表、场景验收集、旧数据兼容清单。既有测试作为兼容回归，批准改变的业务规则注明版本和理由。

验收：可以明确回答“哪些决策给 agent，哪些事实由程序保证”；所有测试期望都能对应业务要求，不依赖源码是否含某段文字。前次串行 589 项测试和类型检查通过；默认并发的短时限敏感用例需消除时序依赖。

**阶段 1：统一学习证据、尝试与状态提交。**

工作：建立 CourseService / CourseRepository、AttemptStore 和证据对象；统一 CLI、RPC 和流程的结算。修正抽样摸底覆盖未测记录、刷题回执与版本保护、小测逐题断点、重建提交窗口。将成绩、能力判断、记忆和教学进度分开。

交付：版本化状态快照、统一提交接口、完整尝试记录、V1 读取适配和恢复机制。

验收：重复提交不重复记分；改答案和过期版本不会覆盖旧尝试；抽样只更新被测证据；任意提交阶段的中断不会暴露半份状态；小测和考试都能从下一道未完成题恢复。一道基础题或核心任务零分不会被解释为目标达成。

**阶段 2：将流程拆成能力，统一结构化事件与内容验证。**

工作：分离“产生内容”“等待用户”“评分”“修改状态”；扩展现有运行时工具注册；输出 question_presented、answer_graded、awaiting_user、activity_paused、content_blocked、activity_completed 等教学事件。拆开集合覆盖、技能范围、目标排除、事实正确性和不确定性。

内容修复成为实际任务：保留失败稿与证据，产生最小候选修订，再接受完整验证。数值用程序复算，代码用隔离执行对照，版本事实引用正文快照；修订资料后相关审查缓存失效。规则只能覆盖自己确定验证的维度，不能忽略语义范围否决。

交付：可调用能力服务、通用工具接口、事件协议、独立修复任务、轻量当前审查状态索引。旧页面通过临时适配器过渡。

验收：能力服务可以无头调用；修改展示文案不会改变作答状态；修复入口实际产生候选内容或明确待处理原因；来源纠错使相关缓存失效；状态查询不扫描全量审查正文。

**阶段 3：实现教学 agent 的最小垂直闭环。**

工作：新增 TutorAgent、精简状态上下文、决策记录与回合协调。先支持一个课程内的解释、诊断、独立任务、回忆和暂停；必要的课程修订可以先生成提案。CLI 和一个网页学习入口接入该闭环。

先使用隔离数据和历史场景回放评估决策，再在独立试学课程启用。现有课程继续使用 V1，避免开发期数据混写。

交付：一个可连续使用、可暂停恢复的 V2 学习会话。每次行动能说明所针对的问题和希望取得的证据。

验收：相同课程在不同学员证据下会产生合理的不同策略；能针对“选择题正确、实际任务失败”选择补测或任务；能针对具体前置回访，而非固定重上整节课；充分达标时可以结束活动。测试评估约束和策略合理性，不强制唯一工具序列。

**阶段 4：实现动态课程、画像与日程决策。**

工作：把课题从固定数量的整课预生成改为目标和时间驱动的近期安排；按需补充后续结构。增加跨单元有效前置、画像假设验证与可追踪的计划修订。多课程根据用户优先级、期限、正在进行的活动和可用时间安排主行动。

交付：可修订的目标图、活动安排、证据驱动画像和每日决策。完整课程规模由教学需要决定，技术输出限制通过分批任务处理。

验收：十分钟与两小时的可用时间会影响行动规模；紧迫期限不能被忽略；不可行目标会形成具体协商提案；临时诊断问题不会自动扩大课程范围；画像变化有证据，未测技能不被清零。

**阶段 5：迁移现有功能、优化查询并补齐执行边界。**

工作：迁移复习、刷题、考试、实践、教研与课程修复；所有入口共享提交和事件。课程首页读取当前决策及查询视图，学习时间采用实际记录或明确标识的活动积分。修复 .mjs 语法、再练按钮和提交失败后的控件恢复，并增加入口与浏览器行为覆盖。

交付：V1 到 V2 的独立迁移工具、旧路由与命令适配、轻量看板、完整功能回归、受限实践执行适配器。

验收：在当前约 170 MiB 的审查历史规模下，重复状态查询以数百毫秒为目标，且耗时不随审查正文线性增长；刷新不计费；多个入口不会互相覆盖；停止后活动有明确状态；自主实践执行无法访问课程状态和模型凭据，网络与资源限制可验证。

**阶段 6：真实试学、逐课切换与旧逻辑收敛。**

工作：完成至少两个不同性质领域的场景验证；在独立学员目录进行试学，记录新题和独立任务表现、提示依赖、等待、恢复求助和成本，再按实际间隔进行次日及一周回访。

交付：逐场景策略与结果报告、失败与未知用量记录、兼容验收与课程切换记录。达到验收后逐课启用 V2，最后移除重复结算、文本业务解析和旧的默认下一步策略。

验收：没有目标越界、错误放行、状态损坏或无法恢复的主要流程；学习结果依据独立测量，不能仅看内部 mastered。小规模试学只作为探索性证据，不能据此宣称普遍教学有效。

### 7. 重点验收场景

| 场景 | 必须验证的业务结果 |
|---|---|
| 有经验学员与零基础学员学习同一目标 | agent 根据证据选择不同起点和检验方式 |
| 选择题正确，但独立编程任务失败 | 不宣布目标达成，选择有针对性的诊断或教学 |
| 已完成课程中的一个前置出现遗忘 | 保留历史成绩和学习进度，针对缺口补救 |
| 截止明天与截止一年后；每天十分钟与两小时 | 计划规模、优先级或可行性建议发生合理变化 |
| 课程目标只含加法，里程碑却要求微积分 | 即使集合关系正确，仍阻止语义越界 |
| 关键综合任务零分、其他题高分 | 关键目标不能被总分补偿 |
| 题目或教材版本修正 | 原始证据保留，旧缓存和过期提交不能冒充当前有效 |
| 抽样重新摸底 | 未测节点证据和记忆记录保留 |
| 网络重试、改答案、CLI 和网页同时提交 | 回执幂等，过期版本拒绝，状态不互相覆盖 |
| 作答一题后暂停，或提交中断 | 恢复同一活动、题目和已提交结果 |
| 内容被拒或生成服务中断 | 区分修复和重试；保留候选、原证据与断点 |
| 申论等开放能力目标 | 可以采用开放作答与量规，不强迫四选一 |
| 查看首页、刷新或重放 | 零模型请求，轻量查询 |
| 当天预算用尽 | 保留结果并结束或形成用户可理解的后续安排 |

### 8. 迁移、回滚与评审重点

迁移按课程进行，保留原文件、原始会话、审查与实践作答。历史 score / mastered 导入为带来源说明的旧评定，不补造逐题答案、提示情况或置信度。目标映射不明确时保留原记录并等待后续证据。

未完成的 V1 课堂和考试优先完成或保存原断点，再切换引擎。禁止两套引擎同时写同一课程。V2 试点使用新目录或明确的独立副本。

回滚包括代码和数据两部分。切换后的 V2 证据不能因恢复 V1 代码而被丢弃；必要时导出可对应的结果，无法安全对应的记录完整保留并说明。先保持试点隔离，降低回滚的数据转换负担。

评审最重要的五项选择：

1. 默认教学由一个 agent 统筹，程序保留明确的执行和校验边界。
2. 技能、课堂活动、能力证据和记忆分别建模，目标验收依据量规。
3. 文件存储继续保留，权威学习状态使用单一版本快照和统一回执。
4. 原有流程逐步拆成能力，先完成一个课程的垂直闭环，再全量迁移。
5. 真正的验收包含教学策略、独立学习结果、恢复与成本；工具调用次数不作为自主性的成绩。

主要风险是模型决策质量、画像推断缺乏证据、能力拆分范围过大、旧数据映射和新增调用成本。应通过精简观察上下文、有限工具步骤、具体反例、逐课试点和可恢复提交控制这些风险。

实施首轮建议限定到阶段 3。达到“一个课程内的 agent 能依据证据选择教学动作，并可靠恢复”的验收后，再推进阶段 4 的动态课程和多课日程。
